# 智能好友与群邀请审核 v1.1.18

AstrBot 插件，支持好友申请和机器人收到的群邀请的全自动、半自动审核。模型只负责单项评分；插件本地校验、计算 0～10 分并执行审批。忽略用户主动申请加入群聊的事件。

## v1.1.18 更新说明

本版统一评分标准并减少无效资料：过滤空白、协议占位值及重复展示内容，分别保留群简介与群公告；模型按固定分档引用资料证据，区分“无法判断”与“明确不匹配”。申请内容不再只因非空就加分，未知评分可能改变通过结论时转人工；审批接口失败与已经同意的识别更严格，只有实际成功处理才更新拒绝次数。人工处理后将原建议与实际结果分开展示，避免相反结论混淆。

## 安装与首次配置

要求 AstrBot >=4.12、aiocqhttp / OneBot v11。将本包中的插件目录放入 `data/plugins/astrbot_plugin_smart_request_review`，安装 `requirements.txt` 后重载插件。插件目录下的 `logo.png` 供 AstrBot 面板显示插件图标。

1. 配置 `review_session`，例如 `group:123456789`（审核群）、`private:123456789`（私聊）或 AstrBot 会话标识。不配置时私聊通知配置审批员和 AstrBot 管理员。
2. 设置 `admin_users` 审批员 QQ 列表、审核模式及模型。
3. 初次使用建议保持 `semi` 半自动模式，观察资料和评分后再选择 `auto` 全自动。

文字 `provider_id`、视觉 `vision_provider_id` 使用 AstrBot 原生模型选择器，并保留动态选项兼容，会列出聊天 provider。插件初始化与延迟初始化时刷新选项，只更新内存中的配置 schema、不改动插件目录文件；新增模型后可重载插件并重新打开配置面板。空值使用自动回退，`__current__` 表示当前会话模型，`__auto__` 表示首个已加载聊天模型，原有指定 provider ID 继续有效。视觉配置留空时先复用文字审核模型；自动选择不代表已验证该模型支持图片。无模型、图片不支持、超时或非法 JSON 时，该项目显示“未知，计 0 分”。

## 审核方式

- **全自动**：按硬规则或分数决定同意/拒绝，接口成功后通知审核会话和申请人/邀请人。接口失败只报告失败。
- **半自动**：完成资料采集、硬规则检测和评分，发出“图片卡片＋短文本”的同一条消息，等待审核员最终决定。
- **全自动资料不足和零分兜底**：全自动模式下，若最终总分为 0、已完成评分项的最高分合计达不到阈值，或当前分数低于阈值但未知项目的分数可能改变通过结论，则发送待审批卡片交人工决定；卡片显示「需人工判断」和具体原因。总分为 0 时即使阈值为 0 也转人工。命中本地黑名单、拒绝关键词或其它硬规则仍按规则自动执行；可用 `auto_manual_fallback` 关闭兜底。
- **本地用户/群黑名单例外**：在两种模式下均自动拒绝。拒绝关键词优先于允许关键词；半自动命中关键词、白名单仍需人工确认。

必须引用机器人发出的对应审核消息使用：

```text
同意
拒绝 [理由]
拉黑 [理由]
```

三条命令均不支持用 QQ 或申请编号代替引用。系统核对消息 ID、机器人、平台、会话、有效期和处理状态；并发审批只执行一次，同一申请的其他通知副本同步标记已处理。“拉黑”先成功拒绝，再加入本地用户黑名单。

引用使用原始 OneBot reply 消息 ID，不采用适配器查询引用详情后替换的 ID；会话归属使用真实群号或私聊对象，兼容开启群聊会话隔离的环境，且不从引用文本解析申请身份。仍提示找不到记录时，日志会给出本次匹配的机器人、平台、会话和引用 ID，便于核对协议端差异。

半自动卡片底部固定总结“建议同意”“建议拒绝：理由”或“建议拉黑：理由”。只有建议拒绝且本次拒绝将达到次数上限时才建议拉黑；模型不能自行决定拉黑。执行前再次检查黑名单，旧卡片不能绕过后来新增的用户/群黑名单。

### 审批结果的幂等处理

审批接口返回的实际状态可能与请求不一致，插件按真实状态记录，不伪造成功或失败：

- 执行“同意”时，只有接口明确返回 `already agree msg by self` 等“机器人此前已同意”文案，才按幂等结果记为“已同意（接口提示此前已同意）”；单独的 `retcode=1200` 不能证明已同意。失败原因按 `wording`、`msg`、`message` 顺序读取。
- 执行“拒绝”时，即使接口返回上述已同意文案或 `matching group request not found`，也不会把拒绝记成同意。插件会短暂重试群列表；只有确认已入群且退群接口成功，才记为“已拒绝（已入群，已退出群聊）”。成员状态无法确认、确认未入群但拒绝接口仍失败、或退群失败时，保留真实错误，不累计拒绝次数、不触发累计拉黑。

## 资料和评分

好友采集 QQ、昵称、等级、签名、验证信息、头像和协议端可用的性别/地区；等级兼容 SnowLuma 的 `qq_level`、`qqLevel`、`level` 字段。群邀请按照 relationship 的申请模型，调用 `get_stranger_info(user_id=邀请人)` 和 `get_group_info(group_id=群号)` 获取资料；群资料不完整时再用 `get_group_info(group_id, no_cache=True)` 重试，必要时调用 `get_group_list(no_cache=True)`，并按本次 `flag` 或群号＋邀请人从 `get_group_system_msg(group_id, only_pending, count)` / `get_group_ignored_notifies` 精确补充收件箱中的群名和邀请人昵称。群号与邀请人取自本次申请；邀请附言若存在仍会显示在卡片中，但不参与评分。群名称、备注、简介、人数/上限和等级只使用有效字段。尚未入群时标准接口仍可能返回空资料；此时隐藏空字段、对应项计 0 分，详细原因保存在历史中。群邀请事件带有 `invited_id` 时只由目标机器人处理，避免多 OneBot 账号重复审核。

资料进入评分和卡片前会清理空白、不可见字符、CQ 标记，以及 `unknown`、`null`、`未知`、`未设置`、零值计数等协议占位信息。群资料的 `group_description`（简介）与 `group_memo`（公告或备注内容）分别保留；内容相同时只展示一次，避免把同一段资料重复当作判断依据。接口无法提供的资料保持缺失，不编造内容、不为缺失字段凑分。

清洗只影响展示与评分，黑白名单关键词仍检查保留的原始申请附言；已有关键词配置不会因占位值过滤而失效。群资料完整但邀请人昵称或附言缺失时，也会尝试精确匹配申请收件箱补全。

| 对象 | 默认评分项 |
| --- | --- |
| 好友 | 验证信息质量 3、申请内容规则 1、QQ等级 2、头像识别 2、昵称识别 1、签名识别 1 |
| 群邀请 | 群资料特征 3、群人数 2 |

每项可单独启用、设置最高分；模型项目可单独设置提示词。本地等级和人数项目使用配置阈值。QQ 默认 15 级加 1 分，更高等级阈值与分数可配置。总分封顶 10 分（群邀请启用项合计 5 分），达到通过阈值（含等于）才通过。

模型评分统一使用整数分档：0 分表示可以判断但没有目标匹配证据；中间分表示部分匹配；满分要求直接、具体的证据。最高分为 1 的项目只允许 0/1 二元判断。理由必须引用已提供文字或可见图像特征，不根据头像、昵称推断真实身份或信息真实性。资料无法辨认、模型能力不足时返回 `unknown:true`、`score:0`、`hit:false`；能判断但不匹配则为已评分 0 分。`hit` 必须与正分一致，理由不能为空；非法 JSON、重复字段、类型错误和冲突的分数均降级为未知。旧版四字段 JSON 与自定义提示词继续兼容，运行时会追加统一标尺，不覆盖已有提示词配置。

“申请内容规则”使用本地固定规则：缺失内容记未知；仅有通用问候、纯数字、重复字符等缺少可辨识申请内容时计 0 分；提供有效内容且未命中拒绝规则才获得本项配置分数。它不证明申请人真实可信。等级、人数也只按配置阈值计分，模型不会重复替这些项目加分。

`friend_score_threshold` 与 `group_score_threshold` 分别控制好友/群邀请：好友默认继承旧 `score_threshold`（默认 5），群邀请默认 3（启用项合计 5 分）；设为 -1 表示继承统一阈值，0～10 为独立阈值。未知资料记 0，关闭、未知和硬规则跳过各有独立标识；白名单直接通过不会伪装成满分。

“有效评分依据”按已完成评分项目的最高分占全部启用项目最高分的比例计算。例如完成权重 4、启用权重 10，覆盖为 40%；这表示评分资料覆盖程度，不是模型置信度或申请人可信度。全部评分项关闭时明确显示无可评分项，不再显示误导的 `0/10`。

### 阈值标定参考

协议端拿不到的资料不会计分，所以每种申请的**已评分项最高分合计**不同。开启自动兜底且未命中硬规则时，阈值高于该上限会转人工；即使上限足够，未知项目若可能改变当前不通过结论，也会转人工：

| 申请类型 | 资料情况 | 已评分项满分合计上限 |
| --- | --- | --- |
| 好友 | 资料全部可得 | 10 |
| 好友 | QQ 未附验证信息（常见） | 6（验证信息质量 3、申请内容规则 1 不可得） |
| 好友 | 陌生人资料为空、头像下载失败且无验证信息 | 0 |
| 群邀请 | 机器人已在群内 | 5 |
| 群邀请 | 未入群，标准接口与申请收件箱均无有效群资料 | 0 |

例如好友阈值设为 6：无验证信息时等于要求等级、头像、昵称、签名全部拿到且拿满，建议改为 4～5。群邀请默认 3（上限 5）。

卡片只显示获取到的头像和有效资料、硬规则、逐项得分/上限/理由、加分算式、总分/阈值和拒绝次数。无头像不显示占位图；空字段和查询错误不展示，评分项仍标记未知并计 0 分。附带短文本显示好友昵称/QQ，或群名、邀请人昵称/QQ、群号。长资料截断并标注，完整文字保存在历史中。头像读取完整响应并校验解码、主地址失败时尝试备用地址，同一张头像用于模型识别和卡片展示；下载失败或数据损坏时该项计 0 分。头像下载失败继续审核；渲染或图片发送失败回退文字。默认显示完整 QQ，`mask_qq_in_notice` 可遮挡展示字段中的号码中段。

## 关系管理与完整长图

| 命令 | 用途 |
| --- | --- |
| `好友列表` | 发送全部好友的长图 |
| `群列表` | 发送全部群聊的长图 |
| `退群 <群号或序号或区间>` | 如 `退群 1-3`、`退群 123456789` |
| `删好友 <QQ或@用户或序号或区间>` | 如 `删好友 @用户`、`删好友 2-4` |
| `加审批员 @用户` | 添加配置审批员，也支持 QQ 号 |
| `减审批员 @用户` | 移除配置审批员，不修改 AstrBot 全局管理员 |

列表不需要页码。普通列表直接一张完整长图；超过 110 条自动分成长图，保留连续序号。图片发送失败会尝试拆成较小图片，再退回文字。所有条目都会保留。

序号/区间来自调用者在同一机器人、会话最近一次列表快照，10 分钟有效；过期或重启后需重新查询。5 位及以上单个数字作为真实 QQ/群号，短数字作为序号，区间始终作为序号。执行前重新检查目标是否仍在列表中。

AstrBot 管理员、配置审批员均可执行关系管理和增减审批员命令。审核群群主/管理员只获得审批权限，不因此获得关系管理权限。所有群内命令只在配置审核群受理；授权管理员和审批员也可私聊使用。

## 被踢拉黑

`kick_block_user` 和 `kick_block_group` 默认开启，分别控制踢人用户和被踢群聊的本地拉黑。处理 `group_decrease/kick_me`，兼容 `kick` 且被踢成员确为机器人自身。踢人用户取 `operator_id`；普通成员被踢、机器人主动退群不触发。缺少有效操作者只按开关拉黑群并记录用户未知。

先持久化，再尝试补全群名和操作者昵称并通知。查询或通知失败不影响名单；审核群正是被踢群时改发配置审批员/AstrBot 管理员私聊。重复事件不会重复记录，也不会增加申请拒绝次数。关闭开关只影响后续事件，不清除已有名单。

用户黑名单同时阻止该用户的好友申请与群邀请，群黑名单阻止其他邀请人再次邀请机器人加入该群。OneBot 没有统一的永久拉黑接口，本插件的“拉黑”是本地名单和后续自动拒绝，不等于 QQ 客户端原生拉黑。

## 多 OneBot 机器人

支持多个独立 OneBot 适配器，也支持多个 QQ 共用一个反向 WebSocket 服务。查询资料、审核通知、申请人通知、审批和关系管理都会携带接收事件机器人的 `self_id`，不修改共享连接的默认账号。待审批记录按平台、机器人、会话和消息 ID 隔离，相同申请标识/消息 ID 不会合并。

审核通知由收到申请的机器人发送，短文本显示“受理机器人”。所有 bot 使用当前插件配置的审核目标；如果某个 bot 不在审核群、被禁言或发送失败，会尝试由该 bot 私聊配置审批员/AstrBot 管理员。该 bot 需要能向至少一个目标发送消息。全部投递失败会写入历史和日志，不创建无法引用的待审卡，并允许协议端重新上报该申请时再次投递；不自动轮询或重试已丢失的协议事件。

排查缺失通知时，先在 AstrBot 日志搜索插件名和“收到friend申请”（或“收到group申请”）。有接收记录但未出卡，可继续查该 bot 的通知失败原因；完全没有接收记录时，请检查该 OneBot 账号是否连接、是否上报 request 事件，以及对应平台/配置是否启用本插件。插件无法处理协议端未上报或框架未交付的事件。

## 数据和升级

使用 AstrBot 插件数据目录中的四份 JSON：`pending.json`、`history.json`、`blacklist.json`、`rejections.json`，自动恢复新版本待审批消息、历史、名单、来源和拒绝次数。默认同一好友/群邀请人按申请类型累计拒绝 3 次加入用户黑名单；成功通过后清零对应类型计数。待审批默认 72 小时过期。`history_limit`（默认 2000）控制历史与来源记录保留条数，超出的旧记录会被回收；插件还会每 10 分钟清理过期待审批、去重标记、列表快照与 30 天未使用的头像缓存，因此长期运行下四份 JSON 不会无限增长。头像按内容摘要缓存在数据目录的 `avatars/`，待审批记录只保存摘要，重启后的结果卡可恢复头像。

升级保留旧历史、拒绝次数和黑名单，并启用已有 `groups` 名单。旧版本缺少机器人/会话归属的待审批消息无法安全验证，不接受继续引用审批，需要对方重新申请；已有待审批记录保留，仍有效的旧卡片可以继续引用，但已经发出的图片不会自动更新，旧记录缺少头像缓存时结果卡不补造头像。请在升级前完成旧版未处理的审批。

## 验证

运行 `python -m unittest discover -s tests -v`。回归测试覆盖配置、评分、模型降级、卡片/长图、引用与并发审批、黑名单、被踢事件、关系命令以及配置/文档一致性门禁。测试使用模拟 OneBot/AstrBot 环境，不会连接 QQ 或调用真实模型；协议端实际可获取的群资料和图片能力仍以部署环境为准。
